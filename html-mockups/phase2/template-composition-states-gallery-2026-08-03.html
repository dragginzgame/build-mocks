Template composition — states gallery.

First-pass mock for the template composition system — the project-level area where a creator combines a token type (attribute schema), a source, an asset spec, a set of capabilities, and a variant profile into one reusable, versioned composition, per Design Documentation/Phase2/template-composition-design.md. Each axis is a small, independent, reusable profile — most are optional, and an axis a composition doesn't need is simply absent, never stubbed. A token is assigned a composition explicitly at creation and pins its exact version forever; nothing is re-evaluated later.

03Profile libraryWhere the axis profiles themselves are authored — separately from any one composition, so they can be reused across many. Tabbed by axis. Each profile is tagged by where it lives: studio library (shared across this studio's collections), platform-owned (available to every studio — the six grader source profiles are the first set), or collection-local (scoped to one collection, e.g. a generator's own layer-stack schema — first-class, never forced up to studio level). Promoting a collection-local profile to the studio library is an opt-in copy-up.

05Assignment — an explicit choice at creationA token is assigned a composition once, at creation or import, and permanently pins that exact version — never re-evaluated, never inferred from attribute values. When a token type has more than one composition, adding tokens asks which one applies; a predicate or explicit list can pre-select the answer for a batch, but only as an authoring shortcut in this moment, not a standing rule.

06Per-token exception — pre-Live onlyBefore a token goes Live, an authorised creator/studio admin may waive a required attribute or slot on that one token (with a reason), or add an extra requirement unique to it (e.g. one item carries a signature). Local to the token, audited, and frozen at Live like everything else — never a schema change for the composition itself.

Note (not UI) — status

From template-composition-design.md: this whole system is still a proposal, not yet ratified — ratification is the only remaining gate on the Phase 2 build. Page name ("Compositions") is not yet ruled on; nothing elsewhere in the design docs or existing mocks names this surface, so it's free to change at review. Once ratified: profile/composition/assignment are the three object kinds (§2); the five axes are token type, source, asset spec, capability, and variant, of which only token type is mandatory (§4); profiles may be studio-library, platform-owned, or collection-local, and collection-local stays first-class rather than forced upward (§9); data migration is moot because all project data is wiped before onboarding, so nothing persisted needs converting (§9.1).
