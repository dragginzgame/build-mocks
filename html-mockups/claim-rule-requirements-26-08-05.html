Claim rule — requirements as checkboxes.

Response to the dev note on the Claim rule modal. Today both groups use radios, which reads as "pick exactly one" — wrong for Requirements, which are optional, multiple, and AND-combined. Per the style guide: checkboxes for multi-select, radios for one-of-many, switches for binary settings. So Claim cost stays radios (Free vs Priced is genuinely exclusive) and Requirements become checkboxes, each expanding its own config block when checked. One hard constraint carries over from the vendor design doc: the claim payload supports one NNS neuron id and one SNS neuron id, so "Has a stake" stays a single instance and unsupported combinations must be rejected at save / start / claim time (fail-closed).

Cost — radios
Free or Priced. Exactly one, always required.
Requirements — checkboxes
Zero or more, AND-combined. None checked = anyone can claim.
Not switches
Switches are for binary settings that apply immediately — not for composing a rule set inside a modal.
Payload limit
One NNS + one SNS neuron proof. No second SNS stake requirement until the payload shape expands.

Part B

Which control, and why.

The style guide already settles this: "Checkboxes for multi-select, radios for one-of-many, switches for binary settings." Showcase on grey — these are documentation samples, not product UI.

B1Control semanticsWhy the requirement group is checkboxes and not switches. Switches imply an immediate, self-contained setting; requirements are composed into a rule that is saved as a unit, so they need the checkbox's "part of a set" reading and the disabled state for the not-yet-available option.
